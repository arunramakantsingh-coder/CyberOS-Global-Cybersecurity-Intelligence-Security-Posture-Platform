# CyberOS M2.2 — Global Security OS Execution Plan

## Status
ACTIVE DEVELOPMENT — NOT FROZEN. This document is the locked implementation contract for the next development cycle.

## UI boundary
The public website at `/` is preserved. Product development happens in the authenticated application workspace under the OS routes (currently exposed on local portal port `3100`). Do not redesign the public website while implementing OS capabilities.

## Customer journey
`/login` → tenant identity/context → `/onboarding` → `/organization` → `/command-center` → module workspace → `/operations`.

A customer such as a CRO/CISO must be able to:
1. enter through a customer security login boundary;
2. establish tenant identity and role context;
3. select enabled security capabilities;
4. define cloud, on-premise DC, hybrid, application, network, endpoint and OT scope;
5. register a customer-controlled assessment connector/Kali agent;
6. map discovered assets into the tenant inventory;
7. define authorization, target allowlists and exclusions;
8. submit policy-gated assessment jobs;
9. receive evidence, findings, correlations and reports;
10. continuously view tenant risk from the Command Center.

## Global Security OS modules
Every module must be purpose-built rather than a copy of the same dashboard. Shared chrome is allowed; module content is not.

- Command Center: executive + operational security picture, global/tenant analytics, risk trend, asset/exposure posture, attack paths and critical actions.
- Threat Intelligence: global intelligence + tenant relevance correlation; actors, campaigns, malware, IOC, CVE/KEV, ATT&CK, geopolitical and sector signals.
- Attack Surface: domains, IPs, applications, APIs, certificates, services, exposure and change detection.
- Vulnerabilities: CVE/CWE/CVSS/KEV, exploitability, asset criticality, exposure and remediation verification.
- Security Posture: CSPM/KSPM, data-center hardening, hybrid posture, endpoint/EDR and control coverage.
- Web & API Security: authorized application/API discovery and testing, including injection detection, access-control, authentication, configuration and evidence/retest workflows.
- Network & Hardening: topology, zones, segmentation, firewall/router/switch baseline, remote access and secure architecture assessment.
- Compliance: ISO 27001, PCI DSS, DORA, SOC 2, NIST and evidence/control mapping with issue lifecycle.
- Cyber AI: evidence-grounded analysis, correlation, explanation, prediction and guarded recommendations; no policy bypass.
- Reports: executive, technical, compliance, assessment and remediation evidence packs.
- Operations: authorization, connector lifecycle, job queue, execution policy, evidence and audit ledger.
- Organization: tenant identity, entitlements, environment scope, connectors, asset inventory and configuration.

## Security execution architecture
Control plane owns tenant context, identity, authorization, scope, policy, evidence, audit and reporting. Execution is performed by approved customer-side connectors. The preferred customer-network model is outbound-controlled agent connectivity; CyberOS does not assume unrestricted inbound access to private networks.

Kali is an execution component, not the control plane. The Kali/customer assessment agent must only execute an explicitly authorized capability against an explicitly approved target scope and exclusions. Scan output is evidence returned to the control plane for normalization and correlation.

## Tenant intelligence contract
Global intelligence is reusable across customers. Any correlation involving private tenant telemetry, assets, findings, identity, network or configuration is tenant-derived and must remain tenant-scoped.

Correlation path:
`global intelligence → tenant profile → asset/exposure/finding match → relevance score → confidence/evidence → module propagation → action/report`.
