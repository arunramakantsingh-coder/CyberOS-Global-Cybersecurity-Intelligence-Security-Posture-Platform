# CyberOS M0.2 — Control Plane Verification

## Implemented

- Database-backed demo identity
- Synthetic authorization context
- Capability allowlist
- Target allowlist through demo assets
- Policy-denied job path
- Policy-approved queued job path
- Database-backed execution worker
- Job state transitions: queued -> running -> completed
- Audit events for request/start/completion
- Synthetic evidence record
- UI control for launching a safe demo job
- Recent execution ledger in the portal

## Safety boundary

The M0.2 worker is synthetic-only. It performs no network access, no arbitrary shell execution and no interaction with external targets. The only enabled capabilities are `demo.asset_inventory` and `demo.finding_fixture`.

## Operator verification

From the repository root:

```powershell
docker compose up --build
```

Then open:

```text
http://localhost:3100
```

Open **Attack Surface** or another module and select **Run synthetic job**.

Expected lifecycle:

```text
requested
  -> policy evaluation
  -> queued
  -> worker picks job
  -> running
  -> completed
```

The recent-jobs ledger should eventually show `completed`.

## Health verification

```powershell
docker compose ps
docker compose logs --tail=50 api
docker compose logs --tail=50 worker
```

Expected services:

- PostgreSQL healthy
- API running on host port 8100
- Portal running on host port 3100
- Worker running

## Data verification

The demo control context is available at:

`GET /api/v1/demo/control-context`

Demo jobs are available at:

`GET /api/v1/demo/jobs`

The job endpoint is:

`POST /api/v1/demo/jobs`

## Reset note

The existing PostgreSQL volume may contain the M0.1 schema. M0.2 initialization is performed by API startup and therefore does not require deleting the volume. Avoid `docker compose down -v` unless a deliberate development database reset is intended.
